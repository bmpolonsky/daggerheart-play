# Daggerheart Play

Daggerheart Play — локальный кинематографичный стол для игр в Daggerheart. Приложение работает как статический сайт, хранит данные игры в браузере и может публиковаться на GitHub Pages. Сетевую комнату мастер открывает отдельно; её состояние и пользовательские ассеты синхронизируются через Supabase.

Проект сделан для ручного и полуавтоматического ведения игры: он помогает с листами персонажей, сценами, бросками, ресурсами, раздаткой, заметками, противниками, отдыхами, групповыми/командными бросками, ходами смерти и опциональными P2P-сессиями, но не пытается быть полностью автоматическим движком правил.

## Возможности

- Режим мастера и режим игрока для локальной или совместной игры.
- Миры с общим компендиумом и файлами, отдельными играми внутри мира; основная копия принадлежит браузеру пользователя.
- Листы персонажей, ресурсы, снаряжение, карты доменов, инвентарь и ходы смерти.
- Броски действия Hope/Fear, d20, урон, быстрые кости, преимущество/помеха и ручные модификаторы.
- Лента с карточками бросков, раздатки, отдыха, командных действий и интерактивных действий карт.
- Сцены с токенами, дистанциями, раздаткой, заметками и музыкой.
- Библиотека противников и текущие экземпляры противников в игре.
- Справочники, которые кэшируются на этапе сборки из API `daggerheart.su`.
- Импорт/экспорт для резервных копий и переноса локальных данных.
- Экспериментальная P2P-синхронизация для сессий мастера и игроков.

## Стек

- Preact
- TypeScript
- Vite
- IndexedDB/Dexie для локального хранения состояния и ассетов
- Trystero для экспериментальной P2P-синхронизации
- Three.js для 3D-костей

## UI kit

Интерфейс строится на собственном dark glass UI kit без сторонней библиотеки компонентов. Общие примитивы, правила выбора компонентов, дизайн-токены и ограничения для новых UI-правок описаны в [`src/ui/components/common/README.md`](src/ui/components/common/README.md).

## Запуск

В CI используется Node.js 22. Для воспроизводимой установки зависимостей из lockfile:

```bash
npm ci
npm run dev
```

Production-сборка:

```bash
npm run build
npm run preview
```

Проверки:

```bash
npm run typecheck
npm run test:unit
```

Полный локальный прогон перед релизом:

```bash
npx playwright install chromium webkit
npm run build
npm run test:unit
npx vitest run tests/content/feature-effects-corpus.test.ts tests/content/equipment-effects-corpus.test.ts tests/content/markdown-cleanup-corpus.test.ts tests/content/hope-and-fear-corpus.test.ts
npx playwright test
```

На Linux зависимости браузеров устанавливаются командой `npx playwright install --with-deps chromium webkit`. `npm run test:e2e` объединяет production-сборку и полный E2E-прогон. Конфигурация Playwright запускает Chromium и отдельный набор `webkit-critical` последовательно, одним worker. Выборочный запуск не заменяет полный прогон итогового кода перед публикацией.

По умолчанию пропускаются проверки, требующие отдельной auth-fixture сборки (`DAGGERHEART_AUTH_FIXTURE=1`), реальных сетевых relay/WebRTC (`RUN_P2P_E2E=1`) и генерации галереи (`TRAY_CONTEXT_GALLERY`). Это отдельные режимы, а не отключение падающих основных тестов. Трассировки и снимки неуспешных тестов сохраняются в Playwright test output.

GitHub CI дополнительно выполняет typecheck, unit и E2E. Публикация Pages после push в `main` зависит от typecheck/unit, проверки контента и production-сборки; E2E в CI остаётся advisory и не блокирует развёртывание автоматически. Новые и необъяснённые ошибки нужно разобрать; подтверждённый флейк оценивается отдельно и не должен автоматически блокировать срочный хотфикс. После публикации проверяются конкретный commit, результат Pages и доступность сайта.

## Кэш и офлайн

В production-сборке service worker автоматически кэширует посещённые статические ресурсы (до 120 записей). HTML загружается из сети при открытии страницы; изображения, шрифты и справочные данные обновляются в фоне. API и внешние сервисы в обычный кэш не попадают. В dev-режиме SW не регистрируется.

Полная подготовка находится в **Настройки → Игра → Офлайн**. Она сохраняет оболочку приложения со всеми JS/CSS-модулями, справочные данные и медиа текущей игры. Файлы, уже загруженные в IndexedDB, не скачиваются повторно. По желанию можно включить **Все иллюстрации справочника**: встроенные изображения и медиа пользовательских записей, даже если они ещё не добавлены в текущую игру. Рядом показывается примерный размер встроенной библиотеки; пользовательские файлы скачиваются дополнительно. По умолчанию опция выключена, а после успешной подготовки выбор сохраняется вместе с офлайн-копией. Недоступные изображения и музыка пропускаются с предупреждением в конце подготовки. Повторная подготовка снова пытается их скачать. Ошибка обязательного файла приложения или нехватка места прерывает подготовку, сохраняя предыдущую рабочую копию.

Подготовленный режим фиксирует версию приложения. Чтобы получить обновление, нажмите **Отключить офлайн** и перезагрузите страницу; обычный кэш и игровые данные остаются. После добавления материалов или смены игры подготовку нужно повторить. Это локальная игра на одном устройстве, а не автономный сервер для сетевых комнат. Данные привязаны к браузеру и адресу сайта; очистка браузерного хранилища удаляет и кэш, и локальные игры.

Для второго экрана можно открыть ещё одно мастерское окно в том же профиле браузера и скрыть его боковые панели. Сохранённое игровое состояние синхронизируется локально между окнами; видимость панелей независима. Второе окно сохраняет мастерский доступ к скрытым материалам и следует выбранной мастером сцене.

Проверка: `npm run build`, затем `npx playwright test tests/e2e/offline.spec.ts --project=chromium`. Для проверки размещения в подпапке: `VITE_BASE_PATH=/daggerheart-play/ npm run build`, затем `OFFLINE_TEST_BASE=/daggerheart-play npx playwright test tests/e2e/offline.spec.ts --project=chromium --project=webkit-critical`.

## Сетевые комнаты

Серверный режим использует Supabase Auth, Postgres, Realtime и Storage. Мастер входит через Google или ссылку на почту только при открытии комнаты; игрок подключается по короткому коду через скрытую анонимную Supabase-сессию. Структурное состояние хранится небольшими JSON-фрагментами, а не одним документом. Для сборки нужны публичные переменные:

```bash
VITE_DAGGERHEART_SUPABASE_URL=https://your-project-ref.supabase.co
VITE_DAGGERHEART_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
```

При наличии этих переменных мастер может выбрать облачную или прямую P2P-комнату. Игрок сначала ищет комнату в Supabase, а при её отсутствии подключается напрямую по тому же шестизначному коду.

Сборка canary для Sites:

```bash
npm run build:sites
```

Миграции и Edge Functions находятся в `supabase/`. Функция `turn-credentials` получает Cloudflare TURN credentials только для участника активной комнаты; долгоживущие секреты задаются в Supabase:

```bash
TURN_KEY_ID=your-turn-key-id
TURN_KEY_API_TOKEN=your-turn-key-api-token
DAGGERHEART_ALLOWED_ORIGINS=https://your-extra-origin.example
```

## P2P signaling

P2P-сессии используют Trystero. По умолчанию auto-режим пробует публичные стратегии `nostr`, `mqtt` и `torrent`. Если настроить Supabase, auto-режим сначала использует Supabase как signaling backend, а затем откатывается к публичным стратегиям.

Supabase нужен только для WebRTC signaling и не заменяет TURN-релей для сложных сетей. Для локальной разработки добавьте в `.env.local`, для деплоя задайте те же переменные в окружении сборки:

```bash
VITE_TRYSTERO_SUPABASE_URL=https://your-project-ref.supabase.co
VITE_TRYSTERO_SUPABASE_ANON_KEY=your-anon-public-key
```

## Кэш справочников

Перед `dev` и `build` запускается:

```bash
node scripts/cache-daggerheart-data.mjs
```

Скрипт скачивает JSON справочников и связанные ассеты в локальные папки `public/data` и `public/image`. Эти сгенерированные папки намеренно игнорируются Git.

Переменные окружения:

```bash
CONTENT_SOURCE=https://daggerheart.su
CONTENT_LANG=ru
CONTENT_REFRESH=1
CONTENT_WEBP_QUALITY=95
```

Для повторного прогона на том же подготовленном корпусе задайте `CONTENT_CACHE_TTL_HOURS=0 CONTENT_REFRESH=0 CONTENT_REFRESH_ASSETS=0` для команд подготовки/сборки. Это переиспользует подходящий кэш; при его отсутствии или смене версии формата скрипт всё равно подготовит необходимые данные. Обновление внешнего корпуса следует проверять отдельно от правок приложения.

До отдельной проверки поддержки при подготовке кэша исключаются карты домена Кровь и подклассы Blood Hunter/Summoner, если их единственный источник — The Void. Существующие справочные записи этих двух классов сохраняются, но в создании персонажа они по-прежнему недоступны. Исключённые записи перечисляются в отчёте обновления. Материалы, переведённые в другой источник, не скрываются этим правилом и проходят обычную проверку корпуса.

`CONTENT_REFRESH=1` принудительно обновляет кэш. Скачанные `png`, `jpg` и `jpeg` ассеты конвертируются в WebP на этапе кэширования без изменения размера. JSON-ссылки переписываются на сгенерированные `.webp` пути.

## Локальные данные

Основная рабочая копия игры принадлежит браузеру пользователя. Открытая сетевая комната дополнительно сохраняет актуальные фрагменты мира и пользовательские ассеты в Supabase, но обычная локальная работа не создаёт серверную сессию.

- Структурное состояние проекта и игр хранится локально.
- Загруженные пользователем ассеты хранятся локально в IndexedDB.
- Импорт/экспорт остаётся основным способом резервного копирования и переноса.
- Очистка данных браузера может удалить локальные игры, если они не были экспортированы.

Экспорт `.dhworld` переносит мир со всеми его играми и общими файлами. Старую `.dhgame` можно импортировать отдельной игрой в текущий мир или открыть как новый мир. Ручные серверные резервные копии мира доступны авторизованному мастеру и не являются автоматической синхронизацией локальных миров.

Сохранение состояния выполняется асинхронно. При прерванной записи приложение может предложить **Восстановление изменений** из локальной копии: она открывается отдельным миром, не перезаписывая исходный мир или изменения других вкладок. Это дополнительная защита, а не замена экспортным резервным копиям. В тестах сценариев «сохранить и перезагрузить» нужно дождаться записи нужных данных мира в IndexedDB; сообщение об успехе отдельного редактора не гарантирует завершения всех связанных записей.


## Sentry

Клиентские ошибки можно отправлять в Sentry при production-сборке:

```bash
SENTRY_DSN=https://examplePublicKey@o0.ingest.sentry.io/0 npm run build
```

Если `SENTRY_DSN` не задан, Sentry не инициализируется. DSN в клиентском приложении не является секретом, но остальные Sentry-переменные окружения не прокидываются в браузер. Для такой сборки Vite публикует source maps рядом со скриптами, чтобы Sentry показывал исходные TypeScript-файлы и строки без отдельного upload token. Ошибки получают контекст операции, транспорта, комнаты и технических идентификаторов, чтобы отличать сбои Auth, Realtime, Storage, TURN, IndexedDB и загрузки справочника. Токены авторизации, содержимое игр, чат, имена, почта и файлы не отправляются.
